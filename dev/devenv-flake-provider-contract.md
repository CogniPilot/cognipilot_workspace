# CogniPilot flake workspace contract

Status: typed v1 contract, locked composition, and atomic package-authority
cutover implemented, 2026-07-14.

`flake.nix` is the canonical CogniPilot project integration entry point. It
already provides pinned inputs, composable outputs, development shells, checks,
and the immutable derivation graph used by `nix build`. CogniPilot should extend
that model with a small flake-parts module for target/artifact/launch semantics,
not introduce a second YAML/TOML project format or a custom provider CLI.

The checked-in root selects external `flakeModules.default` definitions for
the CogniPilot package catalog and exposes one normalized index plus
conventional package/check/shell/app/formatter surfaces. Isolated fixtures prove
the in-tree, external-wrapper, and fork authority forms without polluting the
production product index. The lock is tested offline from a tiny tracked Git
fixture. Editable package authority is complete. Packages remain
qualification-only until they expose faithful immutable deployable outputs;
that release status does not create another editable graph.

The root imports a checked-in flake-parts adapter over devenv 2.1.2's supported
`lib.mkEval` API. The adapter exports only declared dev shells, avoiding the
upstream module's deprecated implicit package/container outputs. One shared
root module supplies the generic `nixspace` client, Git, the Nix-generated
index path, Cachix pull declarations, the default shell, and one
process-compose shell/app per normalized launch.
Editable tasks are generated whenever the shared workspace module is enabled;
package modules repeat none of that wiring.

The generic `nix/nixspace/index-module.nix` and the standalone tool it imports
know nothing about CogniPilot. The small
`nix/cognipilot/nixspace-module.nix` adapter supplies the generic projection
of the already validated CogniPilot index. The generic module validates the versioned
`apiVersion = "nixspace/v1"`, `kind = "Workspace"`, and
`interfaceVersion = 2` envelope and exports `packages.nixspace-index` at
`share/nixspace/index.json`. Devenv passes that store file through
`NIXSPACE_INDEX` and the absolute root through `NIXSPACE_WORKSPACE_ROOT`; it
also binds whichever Nix-generated source, host, and West plan packages are
enabled and installs the Nix-built shell completions. It does not maintain a
second Python or Rust semantic model.
The generic package catalog contains only canonical IDs, aliases, and opaque
namespaced extensions; CogniPilot lifecycle, release, ownership, source, and
compliance policy stays in the provider's validated index and its
`org.cognipilot/package-v1` extension projection.

## Decision

- Each product/workspace selection is a flake composed with flake-parts and
  owns a lock containing only its selected project closure. The default open
  product may live at the repository root; optional/private products use their
  own flake reference and lock.
- Each selected project integration is another flake and exports its reusable
  project definition as `flakeModules.default`.
- A project definition imports CogniPilot's typed flake-parts options once. It
  maps the project's standard `packages`, `checks`, and `devShells` outputs and
  declares the devenv tasks that implement local actions, preventing separate
  handwritten metadata graphs from drifting.
- The root flake imports only the selected project modules. Its
  `packages.<system>.workspace` is the reproducible whole-workspace build;
  product-specific package outputs are deployable release roots.
- Mutable local builds run the devenv task DAG generated by those modules so
  Cargo, CMake/Ninja, npm, west, and Twister keep their native incremental
  state. `nix build` remains the pure/release path.
- Local tasks receive explicit worktree paths at command start; source edits do
  not become path-flake inputs or Nix store copies on the hot build path. Pure
  packages always consume their locked flake source, with an explicit
  command-scoped input override only when testing a local pure build.
- A project with no upstream `flake.nix` is wrapped by a pinned external flake.
  That flake may live in another directory or repository and take the upstream
  source as `flake = false`. A downstream fork may instead carry the flake
  in-tree.
- Zephyr metadata remains owned by west, `zephyr/module.yml`, CMake, and
  Twister. Use `zephyr-nix` for SDK/host-tool packaging and evaluate `west2nix`
  for pure west-project materialization; do not write replacements for either.

This is the Zephyr-like behavior the workspace needs: use a complete in-tree
definition when present, otherwise select a complete external definition or
fork. The root selects one authority and never merges missing fields between
definitions.

## Existing ecosystem assessment

| Tool | What it already solves | Decision |
| --- | --- | --- |
| Nix flakes | pinned recursive inputs, ordinary package/check/shell outputs, immutable derivation DAG, local/remote flake references, non-flake source inputs | canonical project and product entry point |
| flake-parts | distributed reusable flake modules, typed module options, system handling, output composition | canonical composition layer |
| devenv flake module/tasks | shells, mutable task DAG, dependency scheduling, JSON task inputs and outputs, processes | canonical local execution layer |
| west | Zephyr multi-repository manifests, imports/overrides, modules, extension commands, build/flash/debug UX | canonical Zephyr development layer |
| `zephyr-nix` | packaged Zephyr SDKs, host tools, Python environment | use for Zephyr Nix environments after compatibility spike |
| `west2nix` | materializing/building west projects with Nix | evaluate for pure builds; do not duplicate it |
| Omnix (`om`) | generic flake health, output inspection, and CI-oriented Nix builds | use where its normal flake interface fits; do not reproduce it in `nixspace` |
| `nix-fast-build` | parallel evaluation/build of many ordinary flake outputs with cache-aware skipping | use for broad pure-output CI when it outperforms plain `nix build`; never make it an editable-task scheduler |
| Nix Standard (`divnix/std`) | Cells/Blocks output registry and CLI/TUI | useful precedent, but adopting it would replace the current devenv stack and still not supply CogniPilot artifact/launch semantics |
| Blueprint | conventional folder-to-flake-output mapping | too layout-opinionated for this heterogeneous, complex flake graph; its own documentation recommends escaping for complex flakes |

flake-parts is the least-invasive choice: its stated purpose is a distributed
framework for reusable flake configuration, and devenv officially publishes a
flake-parts module. Nix Standard validates that organized target discovery is a
real need, but its larger Cells/Blocks framework is not required to obtain it.

The conventional-tool boundary was rechecked against the upstream interfaces
on 2026-07-13:

- flake-parts already standardizes `flakeModules.default`, per-system outputs,
  and reusable module composition, so CogniPilot adds options to that module
  system instead of writing a flake loader;
- devenv 2.1 tasks already schedule dependency states and exchange typed JSON
  inputs/outputs, so CogniPilot generates task declarations instead of writing
  a scheduler or task protocol;
- Nix Standard's Cells/Blocks add a prescribed output directory structure and
  another CLI/TUI. That does not remove the project-specific artifact,
  variant, or launch contract and would duplicate the selected devenv UX;
- `zephyr-nix` is the SDK/host-tool provider. `west2nix` is a release-path
  candidate where its generated west lock and synthetic Git workspace preserve
  the selected product's manifest/import/module behavior. Native west remains
  the local mutable-workspace authority.

The custom code is therefore restricted to the CogniPilot semantic delta:
typed project/target/artifact/launch options, normalization, compliance, and
planning. Flake composition, immutable derivations, task scheduling, Zephyr
source management, process supervision, and cache transport remain ecosystem
responsibilities.

`nixspace` is justified only by the remaining client-side delta: consume the
versioned normalized document without repeated evaluation, present package,
artifact, resource, and launch records, select an already computed named plan,
and delegate it to Nix/devenv/West/process-compose. It must not grow generic
flake-health checks, pure-output scheduling, a derivation cache, a project
scanner, or a second dependency solver. Those boundaries make the crate useful
to another flake-parts workspace without turning it into a replacement for
Nix's existing CLI ecosystem.

## The three DAGs

One flake definition feeds three related graphs. They must not be confused:

1. Flake `inputs` are the pinned repository/tool dependency graph.
2. Nix derivation references under `packages` are the pure build/release DAG.
3. CogniPilot target/artifact edges generate the mutable devenv task DAG.

Nix automatically constructs (1) and (2). It cannot infer (3) from arbitrary
shell commands or package names: a derivation does not say that one generated C
tree satisfies a specific board build or launch. The CogniPilot flake module
adds only those typed semantics, then generates task edges and normalized index
data from the same option values.

```text
project source or external wrapper flake
                 │
        flakeModules.default
                 │
     root/product flake-parts composition
        ┌────────┼───────────┐
        │        │           │
    packages   checks   devenv.shells/tasks
        │                    │
 pure/release DAG      local incremental DAG
        └────────┬───────────┘
          normalized project index
```

## Project flake module v1

CogniPilot publishes a reusable flake-parts module declaring typed options
under `cognipilot.projects`. A project integration exports one complete module
as `flakeModules.default`; it may also import that module into its own flake for
standalone `nix build`, `nix develop`, and `devenv tasks` use.

The project option schema contains only data not already expressed by standard
flake outputs or a native project tool:

- stable project/package IDs and aliases;
- source identity and whether the integration is Zephyr-backed;
- selectable targets, variant dimensions/defaults/constraints, and actions;
- explicit artifact inputs and typed artifact outputs;
- action resources/exclusive locks and mutable-state policy;
- resources, executable exports, and launch definitions;
- deployability class and corresponding standard package/check output names;
- local-input override constraints and compatibility/interface versions.

The module generates or validates:

- conventional per-system `packages`, `checks`, `apps`, `devShells`, and
  `formatter` outputs;
- devenv tasks and their dependency edges for local actions;
- a JSON-safe normalized index embedded in the root `ws` package/cache;
- structural checks that referenced tasks and standard outputs exist;
- product/workspace package roots composed from selected deployable outputs.

### Authoring budget: package definitions are data

An ordinary package integration must be a small declaration, not another build
script. CogniPilot provides versioned presets for Cargo, npm, CMake presets,
west/Zephyr, and Twister. A preset owns the conventional native commands,
devenv task wiring, standard flake outputs, contract checks, state paths, and
Nixspace-index encoding. The package definition supplies only:

- a stable ID and its source/definition coordinate;
- one preset, when the native project shape is conventional;
- real target, artifact, variant, resource, and launch semantics that cannot be
  inferred from the native project metadata;
- explicit deltas from the preset for genuine exceptions.

Root/product modules provide organization policy and defaults with normal Nix
module priority. They configure cache roots, supported systems, toolchain
policy, compliance checks, and product membership once; project modules never
repeat Cachix settings, scheduler glue, JSON plumbing, state-directory rules,
or generic build/test/check wrappers. Existing conventional flake outputs and
native metadata are referenced, not copied into `cognipilot.projects`.

The minimum fixture for each preset must integrate with one import plus project
data and no handwritten action command. Adding a custom command is an explicit
escape hatch counted as a bespoke adapter during migration. If several
packages need the same delta, it becomes a shared preset capability before the
next package adopts it. This is the boilerplate regression gate; a line-count
limit would reward compressed Nix without preventing duplicated concepts.

Project discovery uses the root flake's explicit inputs and imported modules.
It never scans arbitrary directories or guesses meaning from output names.
After evaluation, list/help/completion commands use the content-addressed
normalized index and do not repeatedly evaluate project flakes.

Do not create one giant root input set containing every optional local checkout.
Flake inputs are static and locked before output selection; an absent path input
or inaccessible private input can otherwise break unrelated work. Each product
flake imports only its closure. Workspace-local source selection is runtime
input to the local task plan, not mutation of the committed product lock.

## Source and definition authority

The root product flake records two independent coordinates:

1. `source`: the exact source tree used by native and pure builds;
2. `definition`: the exact flake module interpreting that source.

A project uses exactly one complete definition origin:

- `in-tree`: the source flake exports its own `flakeModules.default`;
- `external`: a pinned integration flake takes an upstream source input, often
  with `flake = false`;
- `fork`: the selected downstream source revision contains the definition.

The product flake input graph and `flake.lock` pin both coordinates for pure
builds. Local development binds an allowed worktree source in the snapshotted
task plan without changing the flake lock. A command-scoped flake input override
is reserved for evaluating/building the pure package against local Nix/source
changes. Release builds accept only the committed product lock and never read
workspace `devel/` state.

Selection follows west's downstream override principle: the product/root
definition has precedence over imported defaults and replaces a definition as
a unit. It is an error for two imported modules to define the same project ID
unless the root explicitly disables one and selects the other. There is no
field-level fallback, and a fork is visible in the input graph rather than an
implicit patch.

## Zephyr integration

For a Zephyr application or module, the CogniPilot module is deliberately thin:

- west manifests/imports own Zephyr project checkout and revision relations;
- `zephyr/module.yml` owns module build/settings metadata;
- west extensions, CMake, and Twister remain native action entry points;
- `zephyr-nix` supplies the pinned SDK, host tools, and Python environment where
  it supports the selected Zephyr/SDK versions;
- a `west2nix` spike determines whether pure product builds can consume the
  west graph directly without a second hand-maintained source list;
- CogniPilot adds board/target variants, cross-project artifact coordinates,
  product membership, and launches only where Zephyr has no equivalent.

Each product's selected/frozen west manifest closure materializes into a
separate workspace keyed by the complete canonical manifest digest. Product
switches and concurrent builds never mutate another checkout. West's native
`--path-cache` seeds a new workspace from an existing immutable product
workspace before fetching missing pins, while Zephyr's
`EXTRA_ZEPHYR_MODULES` gives editable local modules precedence for local
actions. Locked/release actions omit those overrides. CogniPilot does not merge
every available application manifest into one global west workspace.

An unmodified Zephyr repository can therefore be the non-flake `source` input
of an external integration flake. A project that already has a suitable flake
can export the module itself. A downstream fork replaces the source/definition
explicitly, just as a higher-precedence west project replaces an imported one.

If the `west2nix` spike cannot preserve current manifest-import and override
semantics, pure builds will use explicit Nix source inputs generated and checked
against west output. Native development will still use west; CogniPilot will not
fork west's dependency resolver.

## Local action contract

The module maps every mutable action coordinate to a concrete devenv task.
The workspace supplies one snapshotted normalized plan using devenv's JSON task
input, and tasks publish result JSON through `DEVENV_TASK_OUTPUT_FILE`. Dependent
results are available through devenv's existing task-output mechanism.

Each generated task body is one escaped invocation of the absolute Nix-built
`nixspace _run-task` executable. Nix serializes a versioned `ActionTask` with
the exact working directory, argument vector, literal environment, typed
workspace-root-relative or absolute environment paths, and result. The Rust
client resolves paths against the explicit workspace root, executes that
vector directly, and atomically publishes the declared result only after
success. Devenv still owns DAG scheduling, while Nix remains the sole authority
for the plan and dependency edges.

Tasks must:

- operate on explicit source, state, build, devel, and artifact paths;
- preserve native incremental build directories;
- write only declared output and scratch roots;
- avoid tests, docs, release packaging, network synchronization, and clean
  rebuilds during `build` unless the action explicitly requests them;
- avoid stateful shell hooks and sourced setup requirements;
- emit output paths, kinds, executable modes/symlink targets, and file/tree
  proofs for validation and atomic artifact publication.

Shared flake/devenv modules provide the versioned Cargo, npm, CMake preset,
west, and Twister presets described above. Existing project commands and
Justfiles can remain task implementations when a preset references them.
CogniPilot does not add a `cognipilot-provider` executable or another generic
task scheduler.

## Standard output meanings

- `packages.<system>.default` exists only for one natural immutable product; it
  never means CI or a mutable workspace action.
- Named packages are immutable tools, libraries, firmware/images, bundles, or
  other deployable outputs.
- Qualification belongs under `checks`; explicitly named apps may provide an
  interactive wrapper.
- `devShells.<system>.default` is the normal standalone project environment.
- `formatter.<system>` formats Nix/project configuration owned by the flake.
- Package-specific NixOS modules and overlays may remain, but are not project
  discovery metadata.
- Existing output names remain available while their meaning is mapped
  explicitly in the project module; the workspace never guesses.

Different project flakes may retain different nixpkgs/toolchain pins. Root
`follows` or overrides are opt-in compatibility decisions, never automatic
deduplication. This is essential for ROS, Rust nightly, firmware SDK, and ABI
coupling.

## Shared build-cache contract

Use the standard Nix binary-cache protocol for every pure build. Start with
Cachix because the workspace already documents and consumes Cachix caches and
because it requires no service operation. Attic is the self-hosted alternative;
both remain ordinary Nix substituters, so this choice does not enter project
modules or package identities.

The current public cache is `cognipilot` at `https://cognipilot.cachix.org`, declared
through `cachix.pull` for devenv and by URL/public key in the installation
instructions. Workspace CI uses the official Cachix action in read-only mode
for pull requests and push mode on `main`. Push mode becomes active after a
cache-scoped write token is stored as the `CACHIX_AUTH_TOKEN` GitHub organization
secret. CogniPilot's current policy explicitly authorizes every organization
repository to publish public outputs to this cache.
The product flake advertises the same public URL/key through `nixConfig`, but
enabling flake-provided settings remains an explicit user/admin trust decision;
credentials never appear there.

The product flake exposes a small set of cache roots:

- `packages.<system>.workspace` references every selected immutable product
  output for the default product;
- named product/variant packages reference the other release closures;
- `checks.<system>` contains contract and qualification derivations;
- selected development shells are realized explicitly when their tool closure
  should be pre-warmed.

Protected CI builds the explicit cache and contract roots from the committed
product lock while the Cachix action watches the Nix store and uploads their
closures. Archive and push flake inputs as a separate availability step.
Developer hosts
configure the cache URL and public key as Nix `extra-substituters` and
`extra-trusted-public-keys`; private-cache read credentials stay outside the
flake and repository.

Cache layout follows trust and visibility boundaries, not repository count:

- one read-mostly public cache for open CogniPilot products;
- one private cache for proprietary source/output closures when required;
- optionally, a short-retention development/PR cache that is never trusted as
  a promotion source.

Only organization repositories are trusted publishers, and their workflows
must expose the credential only to protected main/tag CI. Untrusted pull
requests may read the stable cache but cannot write to it. Release product
roots are pinned against garbage collection; branch/PR roots use bounded
retention. CI must build every supported host/target system because store paths
and cache hits are system- and input-specific. The workspace never changes
nixpkgs or toolchain pins merely to manufacture cache hits.

Nix cannot upload mutable devenv task outputs: they are deliberately outside
the store so worktree edits retain Cargo, CMake/Ninja, west, and Twister
incrementality. Use the conventional `sccache` compiler wrapper with a shared
backend for cross-machine C/C++/Rust object reuse, and native package/download
caches for npm/Cargo/west fetches. Deterministic generated artifacts worth
sharing across machines should also be exposed as pure named packages; their
locked form comes from the Nix cache while a dirty local override still uses
the mutable task path. Do not build a CogniPilot-specific remote blob cache.

## Compliance enforcement

Compliance is layered and behavioral. A flake does not pass merely because it
uses the recommended template or exposes similarly named attributes.

1. **Evaluation:** the shared flake-parts module uses option types, assertions,
   and normalized graph validation. Evaluation rejects unsupported interface
   versions, duplicate/invalid IDs, unresolved references, cycles, invalid
   variants, overlapping writable roots, and mutable release inputs.
2. **Standalone project:** importing the module generates
   `checks.<system>.nixspace-interface`. `nix flake check` verifies mapped
   packages/checks/apps, task definitions, locks, and source/definition policy.
   A pinned external wrapper runs this gate for an unmodified upstream source.
3. **Product composition:** the product flake generates a root contract check
   for global namespace uniqueness, cross-project artifact compatibility,
   product closure, input-policy constraints, and pure release references.
4. **Behavior:** shared test fixtures invoke mutable tasks with JSON input and
   isolated state, validate JSON results and content proofs, and exercise
   interruption, concurrency, and write confinement. Pure outputs are tested in
   the Nix sandbox.
5. **Native ecosystem:** Zephyr integrations additionally run west manifest and
   Zephyr module checks; language/package adapters run their native metadata
   validation. CogniPilot validates the mapping instead of copying that
   metadata into its own schema.

The project module declares an explicit interface major. The root supports
exactly one interface major at a time; upgrades are coordinated changes to the
root, selected definitions, and golden fixtures, with no compatibility mode or
runtime fallback. CI requires both the standalone and product contract checks
before a definition can become authoritative. Trusted flake inputs remain a
policy boundary: module compliance is validation, not a sandbox for hostile
Nix evaluation.

## Validation and spikes

Before making this authoritative:

1. Implement the smallest typed `cognipilot.projects` flake-parts module and
   prove it can export/import `flakeModules.default`.
2. Wrap one unmodified non-flake source in an external flake and prove a local
   source override plus locked release source.
3. Compose two existing project flakes into a root `packages.workspace` and
   verify Nix builds the derivation DAG without mutable state.
4. Generate equivalent devenv task edges from the same options and compare
   native incremental performance with the current workspace.
5. Pilot `zephyr-nix` and `west2nix` against CUBS2/cerebri_modules, including
   manifest imports, fork precedence, modules, native_sim, and offline builds.
6. Benchmark cold evaluation and cached list/help/completion. Import only the
   selected product closure if the all-project graph is too expensive or
   fragile.
7. Add structural checks for duplicate IDs, cycles, overlapping writable
   outputs, missing task/package/check references, mutable release inputs, and
   incompatible override pins.
8. Compare Nix Standard on the same two-project fixture once; adopt any useful
   output-discovery convention only if it reduces code without replacing the
   established flake-parts/devenv interfaces.
9. Add a golden minimal fixture for every shared preset. Assert that it needs
   no project-owned task/check/cache plumbing and that semantically equivalent
   in-tree and external definitions normalize identically.
