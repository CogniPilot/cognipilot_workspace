# RDD2 developer workflow

Use one `rdd2` profile for West development, firmware, SIL builds, BIL mission
tests, and deployment:

```yaml
# devenv.local.yaml
profile: rdd2
```

Enter it with `devenv shell`, or prefix a one-off command with
`devenv --profile rdd2`. The profile includes both Zephyr toolchains, RDD2's
isolated West workspace, editable Synapse/CSyn/ZROS dependencies, the local
Rumoca compiler, and the FastDyn/QEMU BIL toolchain.

## Choose the workflow

| Goal | Entry point | Result |
| --- | --- | --- |
| Build flight firmware | `devenv tasks run rdd2:firmware:build` | Cortex-M7 `mr_vmu_tropic` image |
| Configure flight firmware | `devenv tasks run rdd2:firmware:configure` | Project-owned menuconfig for the hardware build |
| Run pure Modelica | `devenv tasks run rdd2:simulation:modelica:test` | Modelica controller and Modelica physics executed by Rumoca |
| Run host SIL | `devenv tasks run rdd2:simulation:sil:test` | 64-bit Zephyr `native_sim`, FMI 3 plant, and mission report |
| Check 32-bit host compatibility | `devenv tasks run rdd2:simulation:sil:build-32` | 32-bit `native_sim` executable |
| Run closed-loop BIL | `devenv tasks run rdd2:simulation:bil:test` | FastDyn/QEMU mission report for the Cortex-M7 binary |
| Compare every simulation fidelity | `devenv tasks run rdd2:simulation:compare` | Gold log, error gates, HTML report, and overlaid plots |
| Flash a controller | `devenv tasks run rdd2:firmware:flash --input confirm=true` | Previously built hardware image |

## West and firmware development

Build the default hardware target:

```sh
devenv --profile rdd2 tasks run rdd2:firmware:build
```

The first build initializes `.devenv/state/west/rdd2/` from RDD2's own
`west.yml`. The task passes editable Cerebri modules, CSyn, ZROS, generated
Synapse C, and the local Rumoca compiler into the project flake. Normal rebuilds
reuse the isolated West checkout and the project build directory.

Expected firmware artifacts are:

```text
src/cerebri_rdd2/build-mr_vmu_tropic/zephyr/zephyr.elf
src/cerebri_rdd2/build-mr_vmu_tropic/zephyr/zephyr.bin
```

Open Kconfig and rebuild without changing profiles:

```sh
devenv --profile rdd2 tasks run rdd2:firmware:configure
devenv --profile rdd2 tasks run rdd2:firmware:build
```

Update West revisions only when intended:

```sh
devenv --profile rdd2 tasks run rdd2:workspace:update
```

RDD2 and CUBS2 never share `.west`, Zephyr, module, or model directories.

## Software-in-the-loop simulation

Build the actual RDD2 application for Zephyr's 64-bit host simulator:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:sil:build
```

The output is:

```text
src/cerebri_rdd2/build-native_sim/zephyr/zephyr.exe
```

Run that firmware against the event-aware FMI 3 plant generated from the same
Modelica package used by the other phases:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:sil:test
```

The task applies RDD2's `tests/zephyr/native_sil.conf`; the resulting binary
uses the direct shared-memory lockstep interface and contains the controller
generated by Rumoca. The runner loads `Vehicles.Rdd2.AvionicsPlant`, reads its
FMI value references from `modelDescription.xml`, flies the bounded mission,
and writes `src/cerebri_rdd2/artifacts/sil/mission.json`. Build the 32-bit
compatibility target separately:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:sil:build-32
```

Its output is under `src/cerebri_rdd2/build-native_sim32/`.

Launching `zephyr.exe` alone is still intentionally incomplete: the project
runner creates and sequences `RDD2_LOCKSTEP_SHM` and advances the FMI plant.

## Binary-in-the-loop mission

Run RDD2's complete closed-loop regression with the hardware-target binary:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:bil:test
```

The task graph:

1. Builds FastDyn's generic Python environment, patched QEMU, plugin,
   device models, and Rumoca support.
2. Builds RDD2 for `mr_vmu_tropic` with RDD2's project-owned Kconfig and
   devicetree overlay.
3. Exports the RDD2 FMI 3 plant and builds the compiled shared-memory/FMI host.
4. Rehosts the Cortex-M7 ELF under QEMU, flies the bounded mission, checks the
   result, and writes JSON and logs.

Principal artifacts are:

```text
src/cerebri_rdd2/build-mr_vmu_tropic-fastdyn/zephyr/zephyr.elf
src/cerebri_rdd2/artifacts/bil/work/cerebri_rdd2_mission.json
src/cerebri_rdd2/artifacts/bil/mission.log
```

The BIL architecture is the ARM Zephyr control binary rehosted by FastDyn/QEMU
with Rumoca physics. It uses the same generated FMI 3 plant and mission logic
as SIL; only the firmware transport changes from a host process to rehosted ARM
memory. The Rust `physics` module is an FMI host and contains no vehicle
equations.

Build all BIL components without running the mission:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:bil:build
```

Adjust the project-owned mission settings with environment variables:

```sh
RDD2_FASTDYN_MISSION_DURATION_S=30 \
RDD2_FASTDYN_PLANT_DT_S=0.01 \
devenv --profile rdd2 tasks run rdd2:simulation:bil:test
```

Other useful settings are `RDD2_FASTDYN_MIN_SPEEDUP`,
`FASTDYN_RDD2_TIMEOUT_SEC`, and `FASTDYN_RDD2_NETWORK_SETUP`. Network setup is
false by default because lockstep uses shared memory; enabling it adds the
privileged TAP/Zenoh communications side channel.

Fresh source syncs start FastDyn's coordinated branch at verified revision
`c235932a60a7bb839e59cac111920fb3b5cbf1aa` until the generic external-
configuration support reaches `main`. Existing source checkouts are fetched
but never switched. If an existing checkout is on `main`, create a work branch
at that revision:

```sh
devenv tasks run sources:sync:FastDyn
git -C src/FastDyn switch -c workspace/cerebri-bil \
  c235932a60a7bb839e59cac111920fb3b5cbf1aa
```

## Cross-fidelity mission comparison

Run the same takeoff, roll command, pitch command, descent, contact, and disarm
mission through the pure Modelica, SIL, and BIL paths:

```sh
devenv --profile rdd2 tasks run rdd2:simulation:compare
```

The common model includes the reusable complementary attitude estimator; RDD2
builds that model as eFMI Production Code for both firmware paths. The plant,
mission schedule, and estimator source are therefore shared rather than
reimplemented for the comparison.

The default canonical logs are:

```text
src/modelica_models/artifacts/vehicles/rdd2/mission-trajectory.csv
src/cerebri_rdd2/artifacts/sil/mission-trajectory.csv
src/cerebri_rdd2/artifacts/bil/work/mission-trajectory.csv
```

The first is the gold log. The comparison bundle under
`src/cerebri_rdd2/artifacts/trajectory-comparison/` contains four PNG plots,
an HTML review report, Markdown, and machine-readable JSON. The test measures
duration, 3-D position, altitude, and wrapped attitude error and fails when a
vehicle-owned limit is exceeded.

Use the `RDD2_TRAJECTORY_*` equivalents of the CUBS2 path and limit variables
to select another log or acceptance budget. A later hardware flight becomes a
gold standard by converting it to
`time_s,x_m,y_m,z_m,roll_rad,pitch_rad,yaw_rad` and setting
`RDD2_TRAJECTORY_REFERENCE` plus `RDD2_TRAJECTORY_REFERENCE_LABEL`.

## Flash and deploy

Flash only with explicit confirmation:

```sh
devenv --profile rdd2 tasks run \
  rdd2:firmware:flash --input confirm=true
```

Select another project-supported runner with `RDD2_FLASH_RUNNER`, for example:

```sh
RDD2_FLASH_RUNNER=jlink devenv --profile rdd2 tasks run \
  rdd2:firmware:flash --input confirm=true
```

Flashing is never a dependency of build, configure, simulation, shell entry,
or process startup.

## Exact task names

Use an exact leaf task from `devenv --profile rdd2 tasks list`. A namespace
such as `rdd2:simulation` selects all descendants, including both expensive
BIL work and SIL builds. It is not a launch preset or alias.

The shared rationale and topology comparison are in
[Vehicle firmware and simulation](vehicle-development.md).
